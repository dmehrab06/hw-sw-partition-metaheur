\subsection{Practical Notes for Rewriting}
When this draft is rewritten manually, the following edits would make the final paper stronger:
\begin{itemize}
\item replace the placeholder author block and title with the actual project naming convention;
\item rerun all experiments with a controlled seed protocol and identical train/eval metrics across methods;
\item convert the draft's repository-derived tables into clean tables generated directly from the rerun outputs;
\item explicitly state whether the final version enables hardware ordering or keeps software-only ordering;
\item add figures showing example schedules, critical paths, or partition visualizations if needed.
\end{itemize}

One subtle but important point deserves repetition. The current ordered implementation can outperform the baseline even when \texttt{use\_hw\_ordering=False}. In that regime, the benefit comes from the software-order head, the changed loss, and the order-aware decode machinery, not from a fully symmetric ordering model over both lanes. A final paper should make this distinction clear to avoid overstating what was actually evaluated.
